# Part 01. 게임 개요 및 핵심 규칙

## 01-01. 게임 콘셉트

### 1. 한 문장 정의 [확정]

**여러 NPC 사이에 같은 외형으로 섞인 2~8명의 플레이어가 서로의 정체를 추리하고 총으로 제거해, 최후의 1인이 되는 1인칭 멀티플레이 위장형 슈팅 게임.**

### 2. 참고 작품 및 차별점 [확정]

- 참고 게임: *Last Man Standing*, *Who's Who?* 등의 NPC 위장·탐색·심리전 장르.
- 과제 조건: 슈팅 요소가 있는 게임.
- 주요 경험: NPC처럼 행동해 정체를 숨기면서 다른 플레이어의 비정상적인 움직임, 조준·사격, 탄약 아이템 획득을 관찰하여 추리한다.
- 핵심 차별점: **제한된 탄약(시작 5발, 최대 10발)과 공개적으로 관찰 가능한 탄약 아이템 획득**을 결합한다. NPC를 무작정 쏘면 탄약을 잃고, 보급받으려 이동하는 행동 자체가 신원 노출의 위험을 만든다.

### 3. 기본 규칙 [확정]

1. 플레이어 인원: **한 방에 2~8명**.
2. 플레이어와 맵에 배치된 다수의 NPC는 **동일한 캐릭터 모델**을 사용한다.
3. NPC는 맵을 **자유롭게 걷고 배회**한다. NPC는 총을 소지하고 걷기/간헐적 정지·둘러보기를 수행하며, 달리기·점프·사격은 하지 않는다(Part 04).
4. 플레이어는 **걷기, 달리기, 조준, 사격**을 할 수 있다. 사격은 **조준 상태에서만** 가능하다.
5. 총에 명중한 NPC와 플레이어는 **한 발에 사망**한다. NPC 사살 자체에 직접 점수 페널티는 없으며 탄약 소비가 실질적 비용이다.
6. 사망한 플레이어는 사망 연출 이후 **라운드 종료 전까지 자유 관전**한다.
7. **라운드(Round)** 는 마지막 생존 플레이어가 정해지면 종료한다(동시 사망 처리 예외는 01-08 참조).
8. 라운드 승리자는 **1점**을 획득한다.
9. **매치(Match)** 는 한 플레이어가 라운드 승리를 **3번 달성해 3점**을 먼저 얻으면 종료한다.
10. 매치 종료 시에만 **1~3위 시상대 연출**을 재생한 후 로비로 복귀한다.

### 4. 플레이 경험의 원칙 [확정/구현 해석]

- **외형만 보고 플레이어와 NPC를 구분할 수 없어야 한다.** 동일한 캐릭터 모델을 사용한다. 의도적으로 플레이어 전용 색/이름표 등을 인게임 캐릭터 머리 위에 항상 노출하는 것은 핵심 규칙에 어긋난다.
- **행동은 단서가 된다.** 플레이어의 달리기, ADS, 사격과 아이템 획득은 다른 사용자에게 관찰될 수 있다.
- **정보 획득에는 위험이 따른다.** NPC 오사격은 목숨을 바로 잃는 벌칙은 없지만, 탄약 낭비와 적의 관심을 끌 위험을 만든다.
- **임의의 라운드 제한 시간은 설정하지 않는다.** 시간 초과로 일률 종료하는 규칙은 현재 요구사항에 없다. 교착을 위한 전원 재시작 투표를 제공한다.

## 01-02. 네트워크·방 구조의 개념

### 1. 세션 방식 [확정]

- **Unity Relay**로 방을 만들고 **Relay 방 코드(join code)** 로 접속한다.
- NGO의 **Host/Client 구조**를 사용한다.
- **방장(Host)이 권한 있는 게임 서버 역할**을 수행한다. 이 문서에서 별다른 구분이 없는 '서버'는 **Relay 인프라 서버가 아닌 NGO Host 프로세스**를 가리킨다.
- Relay는 네트워크 패킷을 전달한다. 사망 판정, 점수, 스폰, 상태 전이 등 게임 규칙을 최종 실행하는 주체는 Host다.
- 방장만 로비에서 **게임 시작**을 실행할 수 있다.

### 2. 로비와 참가자 [확정]

- 참가자는 닉네임을 입력하며, 참가 시 방 코드를 입력한다.
- 방장은 방을 생성해 코드를 발급받는다. 방장 역시 점수판에 표시할 닉네임을 가진다.
- 로비에는 연결된 플레이어 닉네임 목록과 Host의 게임 시작 기능이 있어야 한다.
- 게임 도중 신규 접속은 허용하되, **현재 진행 중인 라운드에는 참여하지 않고 다음 라운드부터** 실제 플레이어로 배치한다.
- 새로 접속한 사람은 **즉시 점수판에 0점으로 추가**한다.
- 일반 플레이어의 접속 종료 시 **즉시 점수판에서 제거**하고 이후 점수·순위 계산 대상에서 제외한다.
- **Host가 나가거나 Host 연결이 끊어지면 방 전체가 종료**되고 다른 참가자는 모두 게임 **메인 화면**으로 돌아간다. Host Migration은 요구하지 않는다.
- 게임 메인 화면의 구성·연출은 **Part 08에서 결정**한다.

### 3. 중요한 경계 조건 [구현 해석]

- **방 접속 여부**, **이번 라운드 참가 여부**, **이번 라운드 생존 여부**는 서로 다른 정보다.
- 새 참가자가 점수판과 재시작 투표 모수에는 포함되더라도, 진행 중인 라운드의 `RoundParticipant`나 승리·패배 판정에는 끼워 넣어서는 안 된다.
- 방 최대 인원 8은 Host를 포함한 **전체 동시 접속 인원 기준**이다.

### 4. 확정되지 않은 로비 값 [추후 확정]

- 닉네임 길이/중복 허용/문자 제한/미입력 처리.
- 방 생성 옵션, 입장 제한 UI, 연결 로딩/실패 메시지.
- 진행 중 입장한 신규 참가자가 다음 라운드 전까지 볼 대기 화면/카메라.
- 게임 인원수가 2명 아래로 떨어졌을 때 다음 라운드를 자동 시작할지, 로비/대기 상태로 보낼지.

## 01-03. 라운드와 매치의 용어·승패

### 1. 용어 정의 [확정]

| 용어 | 의미 |
|---|---|
| 방(Room/Session) | Relay 코드로 접속하는 Host/Client 세션. 최대 8명 |
| 로비(Lobby) | 참가자 목록을 보고 Host가 게임을 시작하는 대기 화면 |
| 매치(Match) | 한 사용자가 **3점에 먼저 도달**할 때까지 이어지는 여러 라운드 |
| 라운드(Round) | 참가자들을 맵에 배치해 **마지막 생존자 한 명**을 결정하는 단위 |
| 라운드 참가자 | 해당 라운드 시작 시 플레이 대상으로 확정된 사람 |
| 접속자 | 현재 방에 연결된 사람. 사망 관전자 및 다음 라운드 대기자 포함 |
| 생존자 | 해당 라운드에 참가했고 아직 Host가 사망 확정하지 않은 사람 |
| 라운드 승리자 | Host 규칙으로 결정된 라운드의 단일 승자. 1점 획득 |
| 매치 우승자 | 라운드 승리 누적 **3점에 최초 도달**한 사람 |
| 시상대 | 매치 종료 후 **상위 3명**을 보여주는 전용 결과 연출. 라운드 종료 때는 사용 금지 |

### 2. 라운드 승리 [확정]

- 기본 승리 조건은 **다른 모든 라운드 참가 플레이어가 사망·이탈하고 생존한 마지막 플레이어**가 되는 것이다.
- **NPC의 생존 여부는 승리 조건에 포함되지 않는다.**
- 라운드 승리자는 **+1점**을 받는다. 사망·처치 횟수·NPC 사살 수로 별도 점수를 부여하는 규칙은 없다.
- **마지막 두 명이 1초 내에 상호 사망**한 경우 양쪽의 사망 연출을 재생하지만, **Host가 먼저 처리한 유효 사망 판정의 공격자**가 라운드 승리자가 된다(01-08).
- 결과 확정은 Host가 딱 한 번 수행해야 하며, **한 라운드에 복수의 승리자/복수의 점수 지급이 발생하면 안 된다.**

### 3. 매치 승리 [확정]

- 특정 플레이어의 라운드 승리 누적 점수가 **3점**이 되면 매치가 끝난다.
- 매치 종료 시 상위 순위 1·2·3위의 캐릭터를 시상대에 배치하고 정산을 보여준다.
- 시상식/정산이 끝나면 **기존 방 로비**로 돌아간다. Host가 `게임 시작`을 누르면 새 매치를 시작할 수 있다.
- 새로운 매치를 시작할 때에는 **점수와 라운드 번호가 새로운 매치 기준으로 초기화**되어야 한다. 이는 매치 단위로 3점을 선취하는 규칙의 **구현 해석**이며, 최초 라운드 번호 표시 형식은 Part 06·08에서 다룬다.

### 4. 기본 종료와 무효 종료를 구분 [확정]

- **정상 라운드 종료:** 단일 라운드 승리자 판정 → 승자 1점 지급 → 약 5초 승리 연출 → 3점 여부에 따라 다음 라운드 또는 시상식.
- **재시작 투표로 무효 종료:** 전원 찬성 → 현재 라운드 무효 → **승자/점수 지급 없이** 다음 라운드 준비.
- **Host 이탈:** 매치 결과 판정 없이 방 해산 → 모든 클라이언트 메인 화면 복귀.

### 1. 상태 정의 [확정 + 구현 해석]

|---|---|---|---|---|

| G02 | Lobby | 방 코드·닉네임 목록·Host 시작 기능 | 참가자/닉네임/접속 관리 | Host가 매치 시작(최소 2명) |
| G03 | RoundSetup | 다음 라운드 준비 | 참가 인원 스냅샷, 모델/NPC/탄약 배치, 상태 초기화 | 배치 완료 |

| G07 | RoundWinnerPresentation | **기존 맵에서 승자가 살아 움직이는 모습을 약 5초 보여줌** | 점수 1회 반영, 카메라 연출 진입 통지 | 연출 완료 |
| G08 | MatchPodium | **시상대 위 1~3위 캐릭터·닉네임·랜덤 가벼운 애니메이션** | 최종 순위 스냅샷·정산 전송 | 정산/연출 종료 |
| G09 | HostDisconnected | 연결 종료 안내 후 메인 화면 복귀 | 세션 파기/종료 | 메인 화면 |

`G06`은 구현상 필요한 **결과 확정 유예 상태**다. '서로 1초 안에 죽으면 양쪽 모두 사망 연출' 요구사항을 지키기 위한 것으로, 모든 라운드를 불필요하게 지연하라는 뜻은 아니다. 세부 판정은 01-08 참조.

### 2. 정상 매치 흐름 [확정]

```text
[메인 화면]
  └─ 방 생성 / 방 코드로 입장
      ↓
[로비: 닉네임 목록, 방 코드, Host 게임 시작]
      ↓ Host 시작
[라운드 준비: 이번 라운드 참가자 확정 및 전체 배치]
      ↓
[5초 카운트다운]
      ↓
[라운드 진행: 위장 / 배회 / 탄약 획득 / 조준 / 사격]
      ├─ 플레이어 사망 → 1~2초 자기 사망 연출 → 고스트 자유 관전
      ├─ ESC 전원 재시작 동의 → 라운드 무효 → [다음 라운드 준비]
      └─ 최후 생존자 판정(필요 시 1초 동시 사망 처리)
          ↓
[라운드 승리자 확정 및 +1점]
      ↓
[현재 맵에서 약 5초 승리자 축하: 승자는 걷기/달리기 가능 (점프 금지), 나머지는 승자를 관전]
      ├─ 승자 점수 < 3 → [다음 라운드 준비]로 반복
      └─ 승자 점수 = 3 → [매치 종료 시상대 / 점수 정산]
                                ↓
                             [로비 복귀]
```

### 3. 전환 시 공통 불변 조건 [구현 해석]

- 라운드 ID(또는 증가하는 세대 번호)를 두어 **이전 라운드의 늦게 도착한 사격·아이템·투표 메시지**가 새 라운드에 적용되지 않게 한다.
- `RoundSetup`이 끝나기 전 5초 카운트다운을 시작해서는 안 된다.
- 매 라운드 시작 시 **참가자/탄약 5발/생존 상태/아이템 개수/투표 상태**를 초기화한다. 점수는 매치 동안 유지한다.
- `RoundWinnerPresentation`은 **맵 안에서** 진행한다. 시상대/메달식 장면을 삽입하지 않는다.
- `MatchPodium`은 오직 3점 도달 이후 한 번만 진입한다.
- 동시 발생 이벤트의 중복 처리로 점수 2회 지급·투표 2회 집계가 일어나지 않게 한다.

### 4. 시간 관련 확정치 [확정]

| 항목 | 값 |
|---|---|
| 라운드 시작 카운트다운 | **5초** |
| 내 캐릭터 사망 시 3인칭 쓰러짐 연출 | **약 1~2초** (정확한 수치 추후 확정) |
| 동시 사망으로 취급할 Host 판정 시간 간격 | **1초 이내** |
| 라운드 승리자 관전 연출 | **약 5초** |
| 매치 시상식/정산 지속 시간 | **추후 확정** |
| 라운드 자체의 제한 시간 | **설정하지 않음** |

## 01-05. NPC와 플레이어의 외형·행동

### 1. 공통 모델 [확정]

- 맵에 있는 **다수의 NPC와 실제 플레이어는 동일한 캐릭터 모델**을 사용한다.
- 같은 종류의 모델링을 사용해 육안으로 구별하지 못하도록 한다.
- 애니메이션은 행동에 따라 달라질 수 있다(걷기·달리기·조준·사망). 실제 클립/상태 머신은 Part 02, 04, 09 참조.

### 2. NPC [확정]

- NPC는 **맵 안을 자유롭게 돌아다니면서 걷기**를 수행한다.
- NPC도 총격에 맞으면 **사망하고 쓰러지는 애니메이션**을 재생한다.
- NPC는 **승리/점수/투표에 참여하지 않는다**.
- NPC 배회 알고리즘·임시 인원 배수·정지/회전·풀링/초기화는 **Part 04**에서 부분 확정하였다. 정확한 생성 위치는 Part 05, NGO 및 네트워크 최적화는 Part 07에서 상세 확정한다.

### 3. 플레이어 [확정]

- 기본 플레이 시점은 **1인칭**.
- 조작 가능한 기본 행동: **걷기 / 달리기 / 조준 / 조준 중 사격**.
- 라운드 승리 후 **같은 맵에서 걷기·달리기 등 자유롭게 축하 행동**을 할 수 있다. **점프는 일반 라운드·승리 연출 모두 불가능**하다 (Part 02 확정).
- 총에 맞으면 즉시 라운드의 생존 자격을 상실하고 사망 연출 후 관전으로 전환한다.

## 01-06. 탄약 경제 및 아이템 보급

### 1. 플레이어 탄약 수치 [확정]

| 속성 | 값 |
|---|---|
| 새 라운드 시작 탄약 | **5발** |
| 탄약 아이템 1개 획득량 | **+5발** |
| 플레이어 최대 보유 탄약 | **10발** |
| 탄약 직접 소모 | **유효한 발사 1회에 1발** |
| NPC 오사격 시 추가 페널티 | **없음** (사용한 1발만 소비) |

수치 예시: 0발인 플레이어가 보급받으면 5발, 4발이면 9발, 8발이면 **최대치인 10발**이 된다. (`min(currentAmmo + 5, 10)`)

### 2. 아이템 생김새 및 상호작용 [확정]

- 맵의 아이템은 단순히 땅에 떨어진 실제 탄약 모델이 아니다.
- **빛기둥, 물음표 상자 등 ‘게임 아이템’임을 한눈에 알아보는 시각적 오브젝트**를 사용한다.
- 플레이어가 **오브젝트에 접촉**하면 별도 '줍기' 입력 없이 탄약을 획득한다.
- 아이템 획득으로 오브젝트가 사라지고 새 위치에 나타나는 변화는 **다른 플레이어도 관찰**할 수 있다. 이것이 중요한 추리 단서다.
- NPC는 탄약을 주워 플레이어처럼 보급받는 역할을 갖지 않는다(현재 정의된 게임 규칙 기준).

### 3. 스폰 개수의 고정 기준 [확정 — 중요]

- 매 라운드 **시작 시점에 배치된 라운드 참가자 수를 `N`으로 스냅샷**한다.
- 해당 라운드의 탄약 아이템은 **항상 총 `N`개가 맵에 존재**하도록 유지한다.
- **라운드 도중 이탈·중도 입장·사망**으로 접속자/생존자 수가 바뀌어도 **그 라운드의 `N`은 변경하지 않는다.**
- 다음 라운드가 시작될 때 신규 참가자/이탈자를 반영해 `N`을 다시 계산한다.

**예시 A:** 5명이 라운드에 참여 → 맵에 아이템 5개 → 그중 2명이 나가도 나머지 라운드 동안 **5개 유지**.  
**예시 B:** 3명으로 라운드 시작 → 중간에 2명이 들어와도 **3개 유지**. 다음 라운드에 5명 참가로 확정되면 **5개 배치**.

### 4. 아이템 획득 후 재배치 [확정]

1. 플레이어가 탄약 아이템의 접촉 영역에 진입한다.
2. 해당 아이템이 획득 처리되며 탄약 +5발(상한 10발)을 반영한다.
3. 기존 아이템은 맵에서 사라진다.
4. **같은 라운드의 다른 무작위 위치**에 대체 아이템이 즉시 나타난다.
5. 논리적인 활성 아이템 개수는 **항상 `N`**을 유지한다.

### 5. 구현상 일관성 [구현 해석]

- 아이템의 **실제 획득·탄약 수 증가·새 스폰 장소 선정은 Host가 확정**한다.
- 동시에 두 사람이 한 아이템을 접촉하더라도 **중복 지급 금지**.
- 아이템 제거/신규 스폰은 서버 상태에서 하나의 교체 작업으로 다뤄 **N+1 중복 생성이나 N-1 영구 결손**이 일어나지 않게 한다.
- 랜덤 위치는 이전 위치와 다른 적법한 후보 위치여야 하고, 플레이어가 접근할 수 있어야 한다. 정확한 스폰 포인트 선정/거리·중복 정책은 Part 05에서 결정한다.
- 네트워크 지연 때문에 각 클라이언트 화면에서 아이템 소멸과 출현이 프레임 단위로 동시에 보이지 않을 수 있어도, Host의 최종 논리 개수는 N이다.

### 6. 미결정 세부사항 [추후 확정]

- 현재 탄약이 **10발일 때 아이템 접촉이 소모로 인정되는지**(획득 불가로 유지 vs 아이템 소모 가능).
- 아이템의 정확한 모델 방향(빛기둥/물음표 등), 색, 이펙트, 획득 사운드.
- 지도상 스폰 후보 위치 개수, 가시성, 안전거리, 드롭 관련 부가 규칙.
- 아이템 접촉 시 동작 애니메이션·소리 노출 수준(접촉 자체 외 추가 연출 여부).

## 01-07. 1인칭 조준·사격·피격의 상위 규칙

### 1. 사격 조건 [확정]

- **조준하지 않으면 사격할 수 없다.**
- 조준에 들어갈 때 **조준 모션(ADS 애니메이션)** 을 재생하고, 무기가 화면 중앙으로 모인다.
- 사격은 클라이언트에서 **Raycast로 1차 명중 대상을 확인**한다.
- 플레이어는 NPC 또는 다른 플레이어를 명중시킬 수 있다.
- 명중한 NPC/플레이어는 **한 발에 사망**한다.
- 사격의 최종 사망 처리 및 순서는 **Host**가 관리한다.

### 2. 명중 처리 흐름 [확정 + 구현 해석]

```text
[사수 로컬] 조준 상태에서 사격 입력
    ↓
[사수 로컬] 발사 즉시 시각·청각 피드백, Raycast로 1차 대상 판별
    ↓
[사수 → Host] 사격 이벤트 / 명중 후보 / 발사 정보 전달
    ↓
[Host] 사격 가능 상태·탄약·대상 유효성 등 검증
    ↓
[Host] 유효 판정 이벤트를 처리 순서대로 기록하고 사망 상태 확정
    ↓
[Host → 모든 클라이언트] 탄약 / 사망 / 애니메이션 / 생존 인원 갱신
```

**권한 주의:** 사용자가 요청한 '클라이언트 1차 Raycast'는 지연에 강한 즉각적인 조작감을 위한 것이지, 클라이언트의 “맞혔다”는 메시지를 무조건 신뢰한다는 뜻이 아니다. Host 검증의 깊이, 발사 시각 보정, 레이 재구성, 위치 이력 저장 여부는 **Part 03·07에서 확정**한다.

### 3. 추후 별도 명세 항목 [추후 확정]

- ADS 전환 시간, 조준 중 이동 허용 및 속도, 시야각 변화. 입력은 우클릭 홀드·사격 후 자동 조준 해제·우클릭 Up→Down 재입력으로 Part 02에서 확정.
- 사격 간격, 발사 효과·사운드, 무기 유형, 손/총 3D 모델.
- 발사 시점 보정/Host 재검증 알고리즘 및 동일 타깃 경쟁 사격 처리.
- 사격 발사·소비 기준(사망 직전 발사 요청, 지연된 요청, 무효 사격과 탄약 소모 정책).
- NPC 또는 플레이어 사망 후 시체 충돌/잔존/제거 정책.

## 01-08. 사망 판정, 동시 사망, 최후 생존자 확정

### 1. 일반 사망 [확정]

- Host가 유효한 총격 명중을 확정하면 대상 NPC 또는 플레이어는 **사망**한다.
- NPC: 쓰러지는 사망 애니메이션 재생.
- 플레이어: 생존자 집계에서 제외 → 자기 캐릭터 사망 연출 → 관전으로 전환.
- 죽은 플레이어는 **해당 라운드가 끝나기 전에는 부활하지 않는다**.

### 2. 1초 동시 사망 규칙 [확정]

- 사망 이벤트의 처리 기준은 **Host가 접수·검증하여 확정한 처리 순서**이다.
- 사망 판정 간격이 **1초 이내**인 경우, 먼저 사망한 플레이어와 나중에 사망한 플레이어가 **둘 다 실제로 죽은 상태로 연출**될 수 있다.
- 특별히 **마지막 2명의 플레이어가 상호 사살**하여 둘 다 사망한 경우, **먼저 Host가 처리한 유효 사망 판정의 공격자**를 라운드 승자로 정한다.
- 따라서 마지막 생존자가 잠정적으로 정해진 순간 게임 결과/연출을 무조건 최종 확정하지 말고, 관련된 **1초 후속 판정**이 들어올 가능성을 처리해야 한다.
- 1초 창의 시작/종료, 누적 이벤트 기록은 **Host 시계**를 기준으로 한다. 클라이언트가 주장한 시각만으로 판정하지 않는다.

### 3. 동시 사망 사례 [확정 규칙에 따른 예]

```text
초기 상황: A와 B, 2명 생존
T = 10.00 : Host가 A의 사격 → B 사망을 첫 번째 유효 사건으로 처리
T = 10.40 : Host가 B의 사격 → A 사망을 두 번째 유효 사건으로 처리
결과      : 화면에서는 A, B 모두 쓰러짐
라운드 승자: A (Host가 먼저 처리한 유효 사망 사건의 공격자)
점수      : A에게만 +1점
```

```text
초기 상황: A와 B, 2명 생존
T = 10.00 : Host가 A의 사격 → B 사망을 처리
T = 11.20 : B의 지연 사격 보고가 도착
결과      : 1초 경과 후 보고는 위의 동시 사망 예외에 자동 편입하지 않음
라운드 승자: A (정상 승리)
```

두 번째 사례의 지연 사격을 **검증상 유효 사건으로 인정할지 자체**는 Part 03·07의 발사 시각/죽은 사수 처리 정책과 연결된다. 여기서 확정한 것은 **1초 예외 범위**이지 별도의 네트워크 보정 정책이 아니다.

### 4. 경합 처리 불변식 [구현 해석]

- Host는 한 라운드 내 사망 판정에 **일련번호**를 부여하여 결정적 순서를 보존한다.
- 동일 대상에 중복 도착한 여러 명중 메시지로 **사망 애니메이션/승리/점수**가 중복 발동되지 않아야 한다.
- 최후의 1인 판단과 1초 동시 사망 창이 서로 충돌하지 않아야 한다.
- 창이 확정된 후 도착한 **이전 라운드의 사격**은 새 라운드를 변경하지 못한다.
- **Host 자체도 플레이어**이므로 Host 사수/피격은 다른 클라이언트와 동일한 게임 규칙을 적용한다.

### 5. 추후 확정할 고급 예외 [추후 확정]

- 사망 처리 직전 이미 발사되었으나 늦게 도착한 요청의 유효성 기준.
- 3명 이상이 1초 이내 연달아 사망하는 복합 상황에서의 정확한 우선순위.
- 한 라운드에서 모두 이탈하여 **승리자를 산정할 사람이 없는 경우** 처리.

## 01-09. 플레이어 사망 이후 카메라와 관전

### 1. 자기 사망 연출 [확정]

1. Host가 플레이어 사망을 확정한다.
2. 죽은 플레이어의 시점을 1인칭에서 **약간 떨어진 3인칭 카메라**로 전환한다.
3. **약 1~2초 동안** 자기 캐릭터가 쓰러지는 사망 애니메이션을 보여준다.
4. 애니메이션 종료 후 **고스트 자유 카메라**로 전환한다.

### 2. 고스트 자유 관전 [확정]

- 고스트 카메라는 **맵 곳곳을 빠르고 자유롭게 이동**할 수 있다.
- 맵의 환경·NPC·살아 있는 플레이어를 둘러볼 수 있다.
- 관전자는 살아 있는 플레이어의 게임 상태에 개입하지 않는다.
- 관전은 그 라운드의 결과 연출 또는 다음 라운드 전환까지 유지된다.

### 3. 관전 구현 세부 [추후 확정]

- 고스트 이동키/상하 이동키·기본 속도·가속·마우스 감도.
- 벽 통과 가능 여부, 맵 외부 이탈 방지 범위.
- 관전 시 다른 플레이어 이름표 표시 여부.
- 관전 UI의 탄약 표시·HUD 숨김/유지 방침.
- 사망 시 카메라 블렌딩·연출 정확한 길이.

## 01-10. 라운드 승리 연출 — **시상대 금지**

### 1. 연출의 위치와 내용 [확정]

- **라운드 종료 시에는 시상대나 시상식 씬을 사용하지 않는다.**
- **플레이하던 맵 그대로** 라운드 결과를 보여준다.
- 화면에는 **'누구 승리(Win)'** 인지 식별 가능한 문구를 보여준다.
- 라운드 승리자는 맵에서 **살아 있는 상태**로 남아 **걷거나 달리며 약 5초간 자유롭게 움직일 수 있다. 점프는 불가능하다**.
- 패배자/관전자는 **3인칭으로 그 승리자를 약 5초 비춰본다**. 관전자들은 승자의 축하 행동을 본다.
- 이후 3점 미달이면 다음 라운드의 전원 재배치 및 5초 카운트다운으로 넘어간다.
- 이번 승리로 3점에 도달했다면 다음 라운드가 아니라 **매치 시상식**으로 넘어간다.

### 2. 카메라 대상 구분 [구현 해석]

| 대상 | 승리 연출에서 하는 일 |
|---|---|
| 라운드 승리자 | 자기 캐릭터를 직접 움직이며 맵에서 축하 행동 (본인 카메라의 정확한 연출 방식은 Part 02·06) |
| 이미 사망한 참가자 | 자유 고스트 관전에서 승리자를 비추는 **3인칭 관전 카메라**로 전환 |
| 다음 라운드 대기 중 신규 접속자 | 현재 라운드 미참가자이므로 관전 진입 UI 방식은 Part 08에서 별도 정의 |

**중요한 구분:** 라운드 승리자의 5초 **맵 내 자유 움직임**과 매치 승리자의 **시상대 포즈**는 다른 기능이다.

### 3. 추후 확정 [추후 확정]

- 승리자 본인 시점이 계속 1인칭인지, 3인칭 축하 카메라로 바뀌는지.
- 라운드 승리 5초 동안 조준/사격 및 아이템 획득을 허용할지. 최소한 **걷기/달리기는 허용**한다. 점프는 불가능하다.
- 패배자 관전 카메라의 위치, 충돌, 보간, 승자를 가릴 때의 처리.
- 승자 텍스트, 효과음, 화면 전환 효과의 정확한 레이아웃.

## 01-11. 다시하기(라운드 무효) 투표

### 1. 기본 규칙 [확정]

- 게임 중 **ESC 메뉴**를 통해 **다시하기 투표**를 할 수 있다.
- 투표 목적은 특정 개인의 기권/항복이 아니라, **현재 라운드 자체를 무효 처리하고 다음 라운드로 넘어가는 것**이다.
- **현재 방에 접속해 있는 전원**이 다시하기에 찬성해야 한다.
- 생존 플레이어뿐 아니라 **사망 후 관전자**도 접속 중이면 투표 대상이다.
- 우측 상단에 `찬성자 수 / 접속자 수` 형식으로 예: **`1 / 3`** 을 표시한다.
- 전원 찬성이 되면 **해당 라운드는 승리자 없이 무효**가 되며 **점수 가산 없이** 다음 라운드가 진행된다.

### 2. 집계 및 연결 변화 [확정 + 구현 해석]

- Host가 동일 참가자의 중복 찬성 메시지를 한 번만 집계한다.
- 접속이 해제된 사람은 즉시 투표의 분자와 분모에서 빠진다.
- 라운드 도중 새로 접속한 사람은 **접속한 전원**에 포함되므로 투표 분모에 반영한다. 신규 접속자는 현재 라운드 참가는 하지 않더라도 투표 주체다.
- 참가자가 떠난 뒤 남은 연결 인원 전원이 찬성 상태가 되면 **투표가 통과**된다.
- 무효 라운드가 종료되면 다음 라운드의 카운트다운 및 참가자 재배치 전에 **투표 집계를 초기화**한다.
- 투표 상태와 무효 처리 확정 권한은 **Host**에게 있다.

**예:** 4명 방에서 3명 찬성 중 1명이 나가서 접속자 수 3명이 되면 `3 / 3`으로 전원 동의가 성립한다.

### 3. UI 최소 요구 [확정]

- ESC 메뉴에는 재시작 찬성 기능이 들어간다.
- 화면 **오른쪽 위**에 투표 진행 수치 `x / y` 표시.
- 로비/매치 종료에서는 진행 중 라운드를 무효 처리할 수 없도록 **상태별 투표 적용 가능 여부**를 제어한다.

### 4. 세부 미확정 [추후 확정]

- 투표 찬성 **철회 가능 여부**, 이미 찬성했을 때 ESC 메뉴 버튼 상태.
- ESC 메뉴가 이동·조준·사격을 막을지 여부.
- 카운트다운 / 결과 확정 유예 / 라운드 승리자 5초 연출 중 투표 가능 여부.
- 투표가 전혀 없을 때 `0 / N` 표시를 숨길지 유지할지.
- 연결 끊김 감지와 분모 갱신의 시간 지연 안내.

## 01-12. 화면 상단 점수판 및 순위 산정

### 1. 게임 HUD 배치 [확정]

- **왼쪽 위**: 방 코드, 현재 라운드 및 점수 순위표.
- **오른쪽 위**: 다시하기 투표 진행 숫자.
- 기본 점수판 텍스트는 **한 줄에 방 코드 + 현재 라운드 번호**를 출력한다.
- 다음 줄은 **반 줄 정도 비운 후** 점수 순위 목록을 배치한다.
- 순위 목록은 **1위부터 닉네임과 점수**를 보여준다.

**왼쪽 위 점수판 예시 (예시 문자열이며 실제 방 코드는 Relay 발급값):**

```text
NFEDF1 3라운드

1위 DFE sdf 3점
2위 Mina 2점
3위 Aki 1점
4위 Player04 0점
```

실제 문구 세부는 UI 파트에서 다듬을 수 있지만 **위치/순서/포함 정보는 확정**이다.

### 2. 순위 정렬 규칙 [확정 — 중요]

1. 가장 먼저 **누적 라운드 승리 점수 내림차순**(큰 점수가 상위).
2. **점수가 같은 양수(1점 이상)** 인 경우, **더 나중에 그 점수를 획득한 사람**을 상위에 놓는다. 실무적으로는 **최근 점수 획득 라운드/Host의 점수 부여 이벤트 순서가 더 큰 사람 우선**.
3. **0점 참가자끼리**는 **방에 먼저 들어온 사람**을 위에 놓는다.
4. 점수판은 점수 획득·신규 입장·접속 종료 시 즉시 갱신한다.
5. 일반 플레이어가 퇴장하면 목록에서 삭제하고 남은 사람들의 순위를 다시 계산한다.

**양수 동점 사례:** A가 1라운드에서 1점, B가 3라운드에서 1점을 획득했다면 **B가 A 위**에 놓인다.  
**0점 사례:** C가 B보다 일찍 입장했고 둘 다 0점이면 **C가 B 위**에 놓인다.

### 3. 정렬 로직을 위한 최소 데이터 [구현 해석]

각 접속자에 적어도 다음 필드를 유지한다.

| 데이터 | 용도 |
|---|---|
| `ParticipantId` (세션 내 고유 식별자) | 닉네임 중복과 무관하게 플레이어 식별 |
| `Nickname` | 점수판/로비/시상식 표시 |
| `Score` | 매치 내 획득한 라운드 승리 횟수 |
| `JoinSequence` | 접속 순서를 Host가 증가하는 값으로 부여. **0점 동점** 정렬 |
| `LastScoreSequence` | 마지막 점수 부여 이벤트의 Host 증가 번호. **양수 동점** 정렬 |
| `IsConnected` | 퇴장 후 순위 계산 제외 |

권장되는 결정적 정렬:

```text
1. Score가 높은 사람이 앞
2. Score > 0 이고 동점이면 LastScoreSequence가 큰 사람이 앞
3. Score = 0 이고 동점이면 JoinSequence가 작은 사람이 앞
4. 안전한 마지막 동률 해소가 필요한 경우 ParticipantId의 안정적 순서 적용
```

점수는 **라운드 승리자가 확정된 순간 한 번만** 업데이트하고, `LastScoreSequence`도 같은 트랜잭션에서 갱신한다.

### 4. 라운드 번호 및 방 코드 [확정 + 구현 해석]

- 예시 포맷: `NFEDF1 3라운드` (방 코드와 라운드 정보를 한 줄).
- `RoundNumber`는 **현재 매치의 라운드 번호**다. 무효가 된 라운드 다음에 새 라운드가 시작되면 새로운 번호를 사용한다.
- 실제 코드 문자열은 Relay가 생성한 **현 세션 참여 코드**를 그대로 표시한다.

### 5. 남은 UI 세부 [추후 확정]

- 인원 8명의 행 간격, 폰트 크기, 순위 강조, 색상.
- 자기 닉네임 강조 여부와 화면 해상도별 반응형 배치.
- 라운드 표시 문자열의 공백·구분자·타이포그래피.
- 매치 도중 점수 0인 중도 입장자의 개인 HUD 및 대기 UI.

## 01-13. 매치 종료 시상대 및 로비 복귀

### 1. 시상식 조건 [확정]

- 어떤 참가자가 **3점**에 최초 도달하면 그 라운드 승리 연출을 거쳐 **매치 종료**한다.
- **1위·2위·3위용 올림픽 메달리스트 형태의 단상(높이가 다른 3단 시상대)** 을 사용한다.
- 순위별 위치에 해당 플레이어의 **동일한 캐릭터 모델**을 배치한다.
- **캐릭터 위에 플레이어 닉네임**을 표시한다.
- 캐릭터별로 **손 흔들기 / 좌우 둘러보기** 같은 가벼운 대기·축하 애니메이션을 **랜덤 재생**한다.
- 시상식에서 점수·순위를 잠깐 정산한 다음 **기존 방 로비**로 돌아간다.
- 방장이 다시 **게임 시작**을 누르면 새 매치를 시작한다.

### 2. 순위 인원 [확정]

- **2명 매치**는 1위·2위만 표시하고 **3위 캐릭터가 없다**. 3위 단상 자체를 장면에 남길지 숨길지는 아트/연출 파트에서 결정할 수 있으나 **없는 3위 플레이어를 생성하지 않는다**.
- **3명 이상**이면 위의 점수판 정렬 규칙을 그대로 적용해 상위 세 명을 시상대에 배치한다.
- 매치 종료 시상대의 동점 순서에도 **최근 점수 획득 우선, 0점끼리는 입장 순서 우선**을 동일하게 적용한다.

### 3. 3점 달성자 퇴장 예외 [확정]

- 플레이어가 **막 3점을 달성해 이미 매치 우승자로 확정된 직후** 접속을 종료하더라도 **시상식까지 진행해도 된다**.
- 이를 안정적으로 구현하려면 **매치 종료 당시의 순위·점수·닉네임·캐릭터 표현 정보를 스냅샷**으로 유지해 시상대 표시를 완료한다. 일반적인 플레이어 퇴장 시 즉시 점수판에서 삭제하는 규칙의 **매치 결과 예외**다.
- 이미 최종 결과가 확정된 매치는 승자의 접속 종료 때문에 취소하지 않는다.

### 4. 매치 종료 이전 일반 퇴장 [확정]

- 3점 달성 전 일반 플레이어가 접속 종료하면 **점수판에서 즉시 제거**하며 더 이상 점수 정산 대상이 아니다.
- 최종 결과가 확정되지 않은 일반 플레이어의 과거 점수를 방 안에서 계속 유지하는 규칙은 없다.

### 5. 추후 확정 [추후 확정]

- 시상식은 별도 씬인지 기존 씬 내 스테이지인지.
- 시상식/점수 정산의 정확한 재생 시간.
- 1위·2위·3위 애니메이션 풀, 카메라 워크, 사운드·UI 레이아웃.
- 참가자가 1명만 남는 등 **3위뿐 아니라 2위도 없는 특수 결과**의 표시 정책.

## 01-14. 라운드 중간 입장·퇴장 및 Host 종료

### 1. 중도 입장 [확정]

- 진행 중 연결한 참가자는 **즉시 로비/세션 참가자 명부와 점수판에 닉네임·0점**으로 등록된다.
- **현재 라운드에는 플레이 캐릭터로 스폰되지 않는다.**
- **다음 라운드 시작** 시 라운드 참가자로 편입돼 다른 플레이어와 동일한 규칙·탄약 5발로 시작한다.
- 진행 중 참가로 인한 **현재 라운드 탄약 아이템 수는 변경되지 않는다**.
- 접속한 전원 투표 규칙에 따라 **재시작 투표의 분모에는 포함**된다.

### 2. 일반 클라이언트 퇴장 [확정]

- 접속 종료 즉시 **연결자 목록과 점수판에서 삭제**한다.
- 해당 참가자가 현재 라운드 생존 상태라면 더 이상 라운드 생존자로 보지 않는다(이탈한 사람은 마지막 생존자/점수 획득 후보에서 제외).
- 이전에 점수를 획득했어도 해당 매치의 이후 순위/점수 계산에서 제외한다.
- 라운드 아이템 스폰 `N`은 그 즉시 감소하지 않는다.
- 재시작 투표의 분자/분모는 접속 종료를 반영해 갱신한다.
- 진행 중 결과가 이미 확정되었고 당사자가 **3점 우승자**인 경우에는 01-13의 시상식 스냅샷 예외를 적용한다.

### 3. Host 퇴장 및 호스트 연결 해제 [확정]

- Host 종료/접속 장애 시 **방은 해산**된다.
- **Host 자동 승계 없음**, 다른 참가자에게 게임 서버 권한을 넘기지 않는다.
- 남은 모든 클라이언트는 게임 로직 중지, 네트워크 연결 정리 후 **메인 화면**으로 복귀한다.
- 미완료된 라운드/매치 점수는 유지할 필요가 없으며, 새 Host를 자동 지정하여 이어서 진행하지 않는다.

### 4. 기술상 주의 [구현 해석]

- 클라이언트가 Host의 장애를 감지하는 데에는 실제 통신 타임아웃이 있을 수 있다. 따라서 **호스트 이탈 즉시 모든 화면이 같은 프레임에 바뀐다는 보장은 요구사항이 아니다**. 접속 장애가 확인되는 즉시 일관되게 메인 화면으로 복귀시켜야 한다.
- Host는 자신의 NGO 서버와 클라이언트의 네트워크 정리 순서를 고려해 종료 처리를 해야 한다.
- 접속 종료 이벤트로 플레이어 목록, 점수판, 투표, 생존자 집계를 함께 갱신해야 한다.

## 01-15. 데이터·이벤트 명세의 최소 계약

> 아래 자료구조·이벤트 이름은 **설계용 추상 계약**이며 최종 C# 클래스명/Unity 컴포넌트명 확정이 아니다. Part 06·07·10에서 프로젝트의 실제 코드 명세로 내린다.

### 1. 세션 참가자 정보

```text
SessionParticipant
  ParticipantId       : 세션 범위 고유 키
  Nickname             : 표시명
  IsHost               : 방장 여부
  IsConnected          : 연결 여부
  JoinSequence         : Host의 접속 순서
  Score                : 현재 매치 라운드 승리 점수(0~3)
  LastScoreSequence    : 마지막 점수 획득 이벤트 순서
  CurrentRoundEligible : 이번 라운드 참가 여부
  IsAlive              : 이번 라운드 생존 여부
  IsSpectating         : 관전 여부
  AmmoCount            : 현재 탄약(0~10)
  RestartVoteYes       : 이번 라운드 재시작 찬성 여부
```

### 2. 라운드 정보

```text
RoundContext
  MatchId                    : 현재 매치 식별자
  RoundId                    : 개별 라운드 식별자(늦은 네트워크 요청 배제)
  RoundNumber                : 현재 라운드 번호
  Phase                      : 준비 / 카운트다운 / 진행 / 판정유예 / 승자연출 / ...
  RoundParticipantIds        : 라운드 시작 당시 참가자 명단 [고정]
  InitialRoundPlayerCount N  : 아이템 개수 산정에 사용할 참가자 수 [고정]
  ActiveAmmoPickupCount      : N 유지
  SurvivingPlayerIds         : 현재 라운드 생존자 목록
  LethalEventSequence        : Host 확정 사망 이벤트의 순서
  FirstRelevantLethalTime   : 최종 판정에서 필요한 Host 시각
  RoundWinnerId             : 확정되면 변경 불가
  RestartVoteIds            : 현재 접속자 중 동의자 목록
```

### 3. 매치 결과 스냅샷

```text
MatchResultSnapshot
  WinnerParticipantId : 최초 3점 달성 플레이어
  FinalRankedPlayers  : [순위, 닉네임, 점수, 캐릭터 표현 정보]
  FrozenAt            : 3점 도달 결과 확정 시점
```

### 4. 필수 논리 이벤트(예시)

# Part 02 — 플레이어 컨트롤러 · 공용 Animator · 1인칭 카메라

> **문서 상태:** v0.3 — 확정 규칙 + 합의된 임시 튜닝값 + 구현 설계안 + 미확정 항목 구분 / 2026-10-12  
> **적용 대상:** 플레이어(2~8명), NPC의 공용 전신 표현, 로컬 1인칭 ViewModel  
> **리소스 상태:** Mixamo FBX 18개를 사용자 PC의 `C:\Users\PC\Downloads\HideAndSeek_Mixamo_Part02`에 **다운로드 완료**. Unity 임포트·프리팹 변경·Animator 에셋 생성은 **미실시**.  
> **용어:** `[확정]` 사용자 결정, `[임시 튜닝값]` 사용자가 초기 구현 기준으로 사용하도록 승인했지만 맵·캐릭터·모델 테스트 후 조정할 수 있는 숫자, `[구현안]` 이후 구현에 활용할 제안 구조, `[미확정]` 사용자 확인 전 임의 확정 금지, `[검수 필요]` 실물 애니메이션 동작을 Unity에서 육안 확인할 대상.

## 02-01. 목표와 구현 불변식

1. **[확정]** 모든 플레이어와 NPC는 동일한 **공개 전신 캐릭터 모델, 총기 모델, 기본 이동 애니메이션 및 Blend Tree**를 이용한다. 모든 캐릭터는 **평소에도 총을 든 모습**이다. 외형으로 NPC/플레이어를 구분할 수 없어야 한다.
2. **[확정]** 플레이어 입력은 1인칭 FPS 기준 `WASD + 마우스 회전`이다. `Left Shift`로 스태미나 제한 없이 빠르게 달린다. 점프는 **라운드 진행 중·라운드 승리 연출 중 모두 불가**다. Space에 점프 기능을 할당하지 않는다.
3. **[확정]** 조준은 마우스 **오른쪽 버튼을 유지**하는 동안 가능하며 조준 중 **WASD 걷기는 가능하고 달리기는 불가능하다.** 조준 상태에서 왼쪽 클릭하면 **한 발을 사격**하고 즉시 조준을 종료한다. 오른쪽 버튼을 계속 누르고 있어도 조준이 자동으로 다시 켜지지 않는다. **오른쪽 버튼을 놓았다가 새로 눌러야 다음 조준**이 가능하다.
4. **[확정]** 사격 가능한 대상은 화면 중앙 크로스헤어 Raycast의 **가장 앞에서 충돌한** NPC 또는 플레이어다. 최종 사망 판정은 Host 권한이다. 판정·탄약 처리는 Part 03 및 07의 계약을 따른다.
5. **[확정]** 로컬 플레이어는 자기 화면에서 전신을 보지 않고 **별도의 손과 무기 1인칭 모델**만 본다. 다른 참가자는 로컬 플레이어의 전신과 총을 정상적으로 본다. 로컬 전신의 렌더링 제외는 네트워크 오브젝트, 물리 충돌 및 다른 클라이언트의 렌더링 상태에 영향을 주면 안 된다.
6. **[확정]** NPC는 정지·보행·간헐적 회전 등을 사용하되, 동일한 공용 Animator 기반으로 표시한다. NPC의 세부 AI/배회 결정은 Part 04.

## 02-02. 입력 계약과 상태

| 입력 | 동작 | 제한/비고 |
|---|---|---|
| `W / A / S / D` | 로컬 전후좌우 이동 | 카메라 수평 방향 기준, 대각선 속도 정규화 [구현안]; **ADS 도중에도 이동 가능** [확정] |
| 마우스 이동 | Yaw(몸체) / Pitch(1인칭 카메라) | FPS 표준, 공개 몸체 Yaw 변화 반영 [확정] |
| `Left Shift` 유지 | 달리기 | 무제한. 조준 중 적용 안 됨 [확정]; 임시 목표 속도 5.0m/s [임시 튜닝값] |
| `Mouse Right Down` + 유지 | ADS 조준 | 새 Press 이벤트 필요. 이전 사격의 홀드로 재진입 불가 [확정] |
| `Mouse Right Up` | ADS 취소 또는 다음 조준을 위한 입력 래치 해제 | 사격 직후 다시 조준하려면 반드시 Up → Down [확정] |
| `Mouse Left Down` | 조준 중 1발 발사 요청 | 일반 상태에서는 무효. 발사 시 기본 상태로 복귀 [확정] |
| `[` | 마우스 감도 1단계 감소 | 감도 화면 안내 표시 [확정] |
| `]` | 마우스 감도 1단계 증가 | 감도 화면 안내 표시 [확정] |
| `ESC` | 기존 라운드 재시작 투표/메뉴 | 입력 차단 세부는 Part 08 [미확정] |

**사격과 조준의 입력 래치 [확정 — 특히 중요]:**

```text
Normal --(RMB Down)--> AimEntering --> Aiming
Aiming --(RMB Up)--> Normal
Aiming --(LMB Down && 발사 가능)--> FireOnce --> Normal/AwaitRightRelease
AwaitRightRelease --(RMB Held)--> AwaitRightRelease [재조준 금지]
AwaitRightRelease --(RMB Up)--> Normal [다음 RMB Down부터 다시 조준]
Any state --(사망 확정)--> Dead [입력 불가]
```

- 조준 종료와 기본 카메라 복귀는 사격 직후 시작한다. 사격 클립은 복귀 과정에서 상체 또는 ViewModel에 재생할 수 있다.
- 탄약 0발·조준 전환 중 클릭·발사 복귀 등은 Part 03에서 확정된 사격 상태 전이 규칙에 따른다. **ADS 애니메이션 완료 전에는 발사 불가, 0발 클릭은 빈 총 소리만 재생하며 ADS 유지**.
- Shift 유지 중 RMB 입력 시 달리기가 중단되고 조준 전환된다. 조준 유지 중 Shift는 달리기를 일으키지 않는다.
- 왼쪽 버튼을 누른 채 오른쪽 버튼을 다시 눌렀을 때 연속 사격이 발생하지 않도록 **LMB Down 에지** 기준으로만 발사한다 [구현안].

## 02-03. 이동 컨트롤러와 회전

**[구현안]** Unity `CharacterController`와 Unity Input System을 사용한다. 뷰 회전은 로컬에서 즉각 처리하고 위치/행동의 타 클라이언트 동기화는 Part 07에서 정의한다. `Animator.applyRootMotion=false`로 두고 이동의 실제 위치 변화는 컨트롤러가 담당하는 구조를 권장한다. NPC는 NavMeshAgent 등 별도 AI 이동기를 사용할 수 있으나, Animator에 전달하는 이동 방향/속도 파라미터의 의미는 플레이어와 공통으로 유지한다.

- `W`는 카메라 수평 정면, `S`는 반대, `A/D`는 좌우 스트레이프. 마우스 Yaw는 전신 모델과 시야를 함께 회전시키고, Pitch는 시야·조준 상체 방향에 전달한다.
- NPC도 회전 상태를 가지며 필요 시 별도 Turn 보행 클립을 쓸 수 있다. NPC 이동이 FPS 플레이어처럼 즉각 방향 전환해야 한다는 뜻은 아니다.
- 걷기 속도는 NPC 보행 속도와 같게 보정해야 한다. 달리기는 다른 참가자가 분명히 알아볼 만큼 빠른 이동·전용 클립을 사용한다.
- **[임시 튜닝값]** 초기 걷기 속도 **2.2m/s**, 달리기 속도 **5.0m/s**, ADS 중 걷기 속도 **1.5m/s**, 이동 가감속 목표 시간 **약 0.15초**. 실제 맵 크기와 플레이 감각이 정해지면 수치를 재조정한다. NPC 정상 보행 속도는 플레이어의 일반 걷기 속도와 일치시킨다.
- **[확정]** ADS 상태에서도 W/A/S/D로 걷고, Shift를 눌러도 달리기를 시작하지 않는다. 달리다가 ADS를 시작하면 달리기를 멈추고 ADS 걷기 속도에 맞춰 전환한다.
- **[미확정]** 회전 보간, 달리기 가능한 입력 방향(앞으로만 vs 측면/후진 허용), 물리 경사·계단 대응 수치, 입력 가감속 모델의 구체적인 수학식. 위 0.15초는 구현 시작을 위한 *목표 반응시간*이고 특정 가감속 함수의 확정이 아니다.

| `moveResponseTime` | `0.15 s` | 가속/감속 목표 체감 시간 | 갑작스러운 전환/발 미끄러짐 |
| `normalFOV` | `75°` | 기본 FPS 월드 카메라 | 시야 왜곡과 맵 스케일 |
| `adsFOV` | `72°` | ADS 월드 카메라 | 스코프처럼 크게 확대되지 않을 것 |
| `adsCameraLocalYOffset` | `-0.08 m` | ADS 시 FPS 카메라 오프셋 | 내려가되 기존 Yaw/Pitch 유지 |
| `adsBlendDuration` | `0.20 s` | ADS 진입/해제 블렌드 | 손·총 애니메이션과 맞는지 |
| `minPitch` / `maxPitch` | `-80°` / `+80°` | 상하 시야 회전 제한 | 위/아래 회전 시 모델 클리핑 |
| `sensitivityMin` / `sensitivityMax` | `1` / `10` | 마우스 감도 단계 | 양끝에서 값 고정 |
| `sensitivityDefault` | `3` | 최초 감도 단계 | 기기별 실제 회전량 별도 조정 |
| `sensitivityStep` | `1` | `[` / `]` 입력 | 정수 ±1 변경 |
| `sensitivityToastDuration` | `1.5 s` | 중앙 하단 감도 안내 | 연속 입력 시 타이머 재시작 |

**구현 주의:** 숫자는 하나의 튜닝 데이터(예: `PlayerMovementSettings`, `FpsCameraSettings` ScriptableObject 또는 SerializeField 설정)에서 관리하고 중복 하드코딩하지 않는다. `moveResponseTime`은 스무딩 목표값이고 `sensitivityDefault=3`은 **감도 단계 숫자**이지 Unity의 특정 마우스 감도 계수가 아니다. FPS 카메라가 ADS로 위치를 옮겨도 크로스헤어는 화면 정중앙을 유지하며, Raycast 방향은 바뀐 카메라 Forward와 일치해야 한다.

## 02-04. NPC·플레이어 공용 Blend Tree 설계

**[구현안]** 두 종류의 캐릭터는 같은 `Humanoid Avatar` 호환 스켈레톤과 같은 **전신 Animator Controller 에셋 하나**를 공유한다. 입력 소스만 플레이어용 LocomotionDriver/NPC용 LocomotionDriver로 나눈다. 각 카메라의 전용 ViewModel Animator는 별개의 애니메이터다.

```text
AC_HumanoidShared.controller [공개 전신 — NPC와 Player 공용]
├─ Base Layer (Override, Weight 1, Humanoid Full Body)
│  ├─ Locomotion Sub-State Machine
│  │  ├─ Walk2D [2D Freeform Directional; MoveX, MoveY]
│  │  │  ├─ ( 0, 0) Idle_ReadyPistol
│  │  │  ├─ ( 0,+1) Locomotion_Forward_Walk
│  │  │  ├─ ( 0,-1) Locomotion_Backward_Walk
│  │  │  ├─ (-1, 0) Locomotion_Strafe_Left
│  │  │  └─ (+1, 0) Locomotion_Strafe_Right
│  │  └─ Run [Locomotion_Forward_Run]
│  ├─ Death [Death_Fall_Back / Death_Fall_Forward / Death_Gunshot_Back]
│  └─ MatchPodium [Victory_Wave / Victory_LookAround 등]
└─ UpperBody Layer (Override, AvatarMask Spine~Fingers)
   ├─ GunReady (기본 상체 대기 또는 Base Layer 통과)
   ├─ AimHold [Aim_Idle]
   ├─ FireOnce [Fire_Handgun]
   └─ AimRelease [Aim_Release_Review: 실제 모션 검수 전 임시 후보]

AC_FirstPersonArms.controller [로컬 ViewModel 전용]
├─ HipIdle
├─ AimEnter
├─ AimHold
├─ Fire
└─ AimExit
```

**Walk2D 규칙 [구현안]:** `MoveX/MoveY`는 *모델의 로컬 공간* 입력 방향이며 각각 `[-1,1]`로 정규화한다. `(0,0)`은 Idle, 양의 Y는 전진. Blend Tree는 걷기 5클립을 결합해 대각선 방향을 합성하고, 달리기는 `IsSprinting` 조건에서 별도 Run state로 전환한다. 정지↔걷기 전환의 damp 시간은 기획상 미확정이므로 검수 후 지정한다. `In Place` 다운로드와 Root Motion Off를 함께 사용하여 애니메이션이 직접 월드 위치를 이동시키지 않게 한다.

**상체 레이어 규칙 [구현안]:** NPC는 평소 GunReady만 사용한다. 플레이어도 GunReady를 기본으로 하고 ADS 중에는 `AimHold`, 사격 시에는 `FireOnce`를 한 번 재생한다. 몸체를 먼저 크게 회전시키거나 총을 꺼내는 방식은 금지하며, 모든 캐릭터의 총은 항상 외부에 노출된다. 획득한 Pistol Walk/Strafe에는 이미 권총 조준 팔 자세가 포함되어 있어, **일반 보행과 실제 ADS의 실루엣 차이가 충분한지 Unity에서 검수해야 한다.** 외형 차이가 불명확하다면 클립 재선정/상체 마스크 조정이 우선이고, 규칙을 바꿔 해결하면 안 된다.

**죽음/시상식 우선순위:** 사망 상태가 되면 Locomotion/Aim에서 즉시 벗어나 Death 전신 클립으로 전환하고, 캐릭터 이동·사격 입력을 막는다. Death 종료 뒤 사망 관전은 Part 01에 따른다. `MatchPodium`은 **3점 선취로 매치 종료 시에만** 재생한다. **매 라운드 종료 5초 연출은 시상식 클립이 아니라 기존 맵에서 승리자가 자유롭게 걷고 달리는 상태**다. 점프는 그때도 불가다.

### 공용 Animator 파라미터 계약 [구현안]

| 이름 | 타입 | 의미 | 작성 주체 |
|---|---|---|---|
| `MoveX` | Float | 로컬 좌우 이동 입력/속도 (-1…+1) | 플레이어 및 NPC locomotion driver |
| `MoveY` | Float | 로컬 전후 이동 입력/속도 (-1…+1) | 동일 |
| `MoveAmount` | Float | 걷기 상태의 이동량 (0…1) | 동일; 필요 시 상위 1D 계층화 |
| `IsSprinting` | Bool | 달리기 모션 표시 | 플레이어 전용; NPC 기본 false |
| `IsAiming` | Bool | 조준 상체 오버레이 | 플레이어 전용; NPC 기본 false |
| `Fire` | Trigger | 유효 발사 1회 | 사격 처리 결과 이벤트 |
| `Die` | Trigger | 최종 사망 판정 1회 | Host 확정 사망 이벤트 |
| `DeathVariant` | Int | 사망 모션 0,1,2 | 사망 연출 선택자 |
| `InMatchPodium` | Bool | 최종 시상식 상태 | 매치 상태 관리자 |
| `PodiumVariant` | Int | 시상식 모션 선택 | 매치 결과 연출 관리자 |
| `AimPitch` | Float | 상하 조준 자세 보조 [선택] | 로컬/원격 표시 로직 |

Animator의 `Die`와 `Fire`는 중복 수신으로 반복 재생되면 안 된다. `InMatchPodium`이 false인 일반 라운드 종료에서 시상식으로 잘못 전환되지 않도록 한다. NPC와 전신 플레이어 모두 동일 controller와 파라미터 정의를 사용하되, NPC에서는 플레이어 전용 트리거를 호출하지 않는다.

### Mixamo 클립을 사용하는 Animator 전환 계약 [구현안]

- `Entry -> Walk2D` 기본, `IsSprinting=true`인 경우 `Run`, false 시 `Walk2D` 복귀. Run 도중 `IsAiming=true`로 이동하면 즉시 Walk2D로 내려가고 상체 AimHold.
- `Die`는 모든 일반 상태에서 우선순위 최상위 전환, 나간 뒤 해당 라운드에서 일반 상태 복귀 금지.
- `Fire`는 UpperBody `AimHold -> FireOnce`; Fire 유효 처리 직후 Base 정상 상태로 복귀하고 `IsAiming=false` 유지. 재입력 래치가 풀리기 전에는 AimHold 재진입 금지.
- 시상식 애니메이션은 `InMatchPodium=true`에서만 전신 랜덤 선택하며 Loop 여부는 클립별 육안 검수. 단순 손 흔들기는 상체만 사용하도록 변경 가능.
- `Turn_Walk_Left/Right`는 **기본 Blend Tree 필수 클립은 아님**. NPC가 방향을 바꿀 때 표현 보강용으로 수집한 후보이며, 회전 속도 및 Root Motion 검수 전에는 기본 상태로 연결하지 않는다.

## 02-05. FPS 카메라 · 조준 · ViewModel

**[구현안] Prefab 기준 계층**

```text
NetworkPlayerRoot  [NetworkObject, CharacterController, Hitboxes, PlayerInputOwner]
├─ WorldVisualRoot [공용 Animator, Humanoid, SkinnedMeshRenderer, GunWorldModel]
├─ FirstPersonRig [로컬 소유자만 활성화]
│  ├─ ViewPivot [Yaw/Pitch 분리 중 Pitch 담당]
│  │  ├─ WorldCamera [기본 1인칭 화면 / 크로스헤어 중앙 기준 Raycast]
│  │  └─ ArmsViewModel
│  │     ├─ HandsMesh
│  │     └─ GunViewModel
│  └─ FirstPersonArmsAnimator
├─ SpectatorCameraAnchor [사망 3인칭 연출 위치 계산용]
└─ DamageableHitboxes [물리 충돌/피격 레이어 유지]

NPCActorRoot [NPC 이동기, 동일 WorldVisualRoot 및 공용 Animator]
└─ WorldVisualRoot [동일 모델, GunWorldModel]
```

- **로컬에서만** 자신의 WorldVisualRoot를 FPS WorldCamera의 Culling Mask에서 제외한다. WorldVisualRoot 자체 GameObject 비활성화, 네트워크 컴포넌트 비활성화, 전신·총기 삭제, Hitbox 비활성화는 금지한다.
- 타인의 WorldVisualRoot와 모든 NPC의 전신/총기는 모든 참가자에게 보인다. 자신의 캐릭터 그림자 또는 사망 연출의 전신 표시는 카메라별 레이어 설계로 대응한다.
- 손과 총은 **로컬 ViewModel 전용**. 타인에게는 별도 손 모델이 보이지 않고 WorldVisualRoot의 총기만 보인다. 필요 시 URP 카메라 스택(Base WorldCamera+Overlay ViewModelCamera) 사용 가능하나 프로젝트 Render Pipeline 확정 전 강제하지 않는다.
- 레티클은 **화면 기하학적 중앙**. 실제 총구 모델 위치에서 Raycast하지 않는다. Raycast 대상 중 **최전방 충돌체** 우선; 장애물 뒤 타격 불가. 자세한 피격 레이어/거리/검증은 Part 03.
- 조준 시 카메라가 약간 내려가고 손·총 모델이 화면 중앙으로 정렬되며 FPS 느낌의 미세한 줌을 준다. **스나이퍼 스코프급 확대가 아니다.** 이미 위나 아래를 바라보던 Pitch를 강제로 0°로 돌리지 않고 시선 방향을 유지한다.
- **[임시 튜닝값]** 기본 `WorldCamera.fieldOfView = 75°`, ADS 목표 FOV `72°`, ADS 카메라 로컬 **Y 오프셋 -0.08m**, 기본 ↔ ADS 전환 **0.2초**, 카메라 Pitch 범위 **-80°~+80°**. 카메라의 기존 바라보던 Pitch/Yaw는 ADS 시 강제로 0으로 변경하지 않는다.
- **[미확정]** ViewModel 근접 클리핑, 실제 총기 조준점 정렬 오프셋, ADS 이동 이징 함수 및 화면 흔들림 등 미적 튜닝값. 75/72°는 WorldCamera의 초기값이고 ViewModel 카메라가 분리된다면 렌더링 파이프라인 결정 후 재검증한다.

### 감도 변경 UI [확정 + 임시 튜닝값 + 미확정]

- `[`/`]` 키 입력 시 조절된 감도를 즉시 적용하며 화면 **중앙 하단**에 작은 텍스트 `감도 : 3` 형태를 띄운다. 입력이 다시 들어오면 같은 안내를 갱신한다.
- **[임시 튜닝값]** 감도 단계는 정수 **1~10**, 초기값 **3**, `[`/`]` 한 번 누를 때 **-1/+1**. 범위 밖 입력은 최솟값/최댓값에 고정한다. HUD는 입력 시 `감도 : 3` 형식으로 화면 중앙 하단에 **1.5초** 표시하고, 그동안 다시 입력하면 숫자를 갱신하며 1.5초 표시시간을 재시작한다.
- **[구현안]** 감도 단계는 사용자가 이해하는 UI 값이므로 실제 시야 회전 계수와의 매핑(`degrees per pixel` 등)은 별도의 직렬화된 설정으로 둔다. 임의의 마우스 회전 계수까지 확정된 것으로 취급하지 않는다.
- **[미확정]** 설정 영속화(재시작 후 유지), 마우스 가속 여부 및 단계별 실제 회전량 배율.
- 실제 감도 값은 카메라 Yaw/Pitch 연산에 동일하게 적용하고 NPC/원격 카메라에는 영향을 주지 않는다.

## 03-02. 입력·애니메이션 상태 전이

**전투 상태 제안 enum:** `HipIdle`, `AimEntering`, `AimReady`, `Firing`, `FireRecovery`, `AimExiting`, `Dead`, `Spectating`. 이름과 정확한 StateMachine 분할은 구현 예시이고 기획상 고정 API 명칭은 아니다.

| 현재 상태 | 입력/조건 | 결과 및 제한 |
|---|---|---|
| 기본 상태 (`HipIdle`) | RMB **Down** | `AimEntering`; 이동은 ADS 저속, 달리기는 즉시 제한, ADS 전용 애니메이션 재생 |
| `AimEntering` | 애니메이션 완료 전 LMB | **무시**. 탄약 소비·총성·Raycast 없음 |
| `AimEntering` | ADS 모션 완주, RMB 아직 유효 | `AimReady` 전환. 사격 가능 |
| `AimEntering`/`AimReady` | RMB Up | 조준 취소 후 일반 카메라·모션 복귀. 재조준에는 새로운 RMB Down 필요 |
| `AimReady` | LMB Down + 탄약 ≥ 1 | 로컬 1발 즉시 발사·총성/반동 재생, Raycast 결과 산출, Host 요청 전송. ADS 종료, `Firing` 진입 |
| `AimReady` | LMB Down + 탄약 0 | 빈 탄창 클릭음 로컬 재생, **ADS 유지**, Raycast 및 Host 피해 요청 없음 |
| `Firing`/`FireRecovery` | RMB를 계속 누름 또는 Down | **재조준 불가**. 발사 애니메이션·복귀 과정이 끝나야 새 조준 가능 |
| `Firing`/`FireRecovery` | 발사 애니메이션 완료 | 기본 상태. RMB가 눌린 채여도 재진입 불가, **RMB Up → 새로운 RMB Down** 필요 |
| 어떤 상태든 | Host 사망 확정 | 조작·사격 비활성화. 전신 Death 클립 전환 → 본인은 근거리 3인칭 사망 연출 → 자유 고스트 관전 |

**입력 이벤트는 Down 에지 기준**으로 처리해 LMB/RMB 홀드만으로 자동 연사·자동 재조준되지 않도록 한다. ADS 전환 시간은 Part 02의 **약 0.2초 임시값**, 조준 중 속도 약 1.5m/s 임시값을 사용한다. 발사 클립이 끝나기 전의 잠금은 확정이지만, 발사 클립 길이와 별도 복귀 보간 시간은 실제 Mixamo/ViewModel 리소스를 적용한 뒤 튜닝한다. 탄약 미보유 상태의 빈 총 소리를 네트워크로 타인에게 전달할지는 미확정이므로 기본적으로 **본인에게만 피드백**하는 구현을 제안한다.

**Animator 계층 계약:** 외부 NPC/플레이어 전신은 공용 `AC_HumanoidShared`를 사용하고, 로컬만 `AC_FirstPersonArms` ViewModel에서 조준·발사/복귀를 표현한다. 유효 발사 때 원격 전신은 상체 FireOnce 모션을 재생할 수 있으나 사망 모션은 Host 사망 확정 이벤트만 원인으로 삼는다. NPC는 사격 능력이 없고 총기 보유 외형/기본 이동 모션만 공유한다. 정확한 타이밍 이벤트(`AnimationEvent`/정규화 시간)는 애니메이션 파일 검수 후 확정한다.

## 03-03. 화면 중앙 Hitscan 명중 판정

1. 발사 조건을 만족하는 로컬 Client가 발사 순간 **현재 FPS 카메라 위치**와 정면 단위 방향을 고정한다. 총구나 손 모델 위치는 명중 판정의 시작점으로 사용하지 않는다.
2. 조준 레티클의 화면 정확한 중앙을 통과하는 Raycast를 실행한다. `Physics.Raycast` 등을 사용하고 범위는 맵 전반을 덮되 유한한 값으로 제어한다(최종 수치 추후 확정).
3. Raycast의 가장 가까운 **단일 유효 충돌**을 채택한다. 벽이나 맵 장애물이 먼저라면 그 뒤의 NPC/플레이어를 명중시킨 것으로 보고하지 않는다. NPC/플레이어의 Capsule이 먼저라면 해당 NetworkObject의 식별자를 명중 후보로 기록한다.
4. 피해를 입는 캐릭터의 Hitbox는 **머리·몸통·팔 구분 없는 Capsule 1개**를 기준으로 한다. FPS 이동용 `CharacterController`가 별도 존재한다면 총격 Raycast는 `Hitbox`/`WorldOccluder` 등 지정된 레이어에만 쏘아 한 캐릭터에서 중복 충돌체로 인식되지 않게 한다. 자기 자신의 몸·손·총·픽업 Trigger 등은 판정에서 제외한다. 구현 세부 Collider/Layers는 Part 05·10에서 확정한다.
5. 빗나가거나 장애물을 맞춰도 탄약 1발은 소비한다. **벽·바닥 맞춤 효과/VFX/탄흔은 전혀 생성하지 않는다.**
6. 총알은 NPC·플레이어·환경을 관통하지 않고, 다중 표적을 동시에 처치하지 않는다.

캡슐의 크기는 초기값 이후 실제 명중 난이도, NPC 배회와 사용자 크로스헤어 체감에 맞춰 조정한다. **NPC와 플레이어는 같은 캡슐 규칙**을 적용한다.

## 03-04. 지연 최소화: Client 1차 판정 / Host 최종 사망 확정

**원칙 [확정]:** `Client`는 **자신이 본 화면에서 즉시 Raycast로 맞았는지까지 판단**한다. 명중 후보를 Host에게 보고하여 **최종 승인만** 받는다. Relay 지연 때문에 Host의 **현재 위치로 다시 Raycast하여 명중 자체를 재판정**하는 방식은 원 의도에 맞지 않으므로 금지한다.

| 단계 | 주체 | 동작 | 시각·청각 처리 |
|---|---|---|---|
| 1 | 사수 Client | ADS 완료·탄약 확인, LMB → 로컬 Raycast·단일 대상 식별 | **즉시 총성 + 손/권총 반동 + 발사 모션**. Host 응답 기다리지 않음 |
| 2 | 사수 Client → Host | 한 발에 한 요청 전송: 라운드 구분, 고유 사격 순번, 발사 레이 방향, 후보 대상 ID·빗나감 정보 등 | **사망 연출은 아직 없음** |
| 3 | Host | 사수의 실제 ClientId와 현재/허용 가능한 전투 상태, 탄약, 중복 요청, 목표 존재 여부, 라운드 세대, 기본 물리 타당성 등을 검증 | 승인 전 죽음 상태 변경 금지 |
| 4 | Host | 승인된 발사에 대한 탄약 최종 반영 및 목표 NPC/플레이어 사망 처리, 요청 순서 기록 | 결과를 전원 동기화 |
| 5 | 모든 Client | Host로부터 승인된 죽음 이벤트 수신 | **이 시점에만 전신 사망 애니메이션**. 사망한 사용자는 별도 본인 3인칭 사망 카메라(1~2초) → 고스트 관전 |

**네트워크 페이로드 제안 [구현 해석, Part 07에서 상세화]:** `roundId`, `shotSequence`, `rayOrigin`, `rayDirection`, `clientObservedTargetNetworkId` 또는 명중 없음, `clientShotTick` 정도를 필요 최소한으로 보낼 수 있다. **`shooterClientId`는 보내온 값이 아니라 RPC 호출자 메타데이터에서 Host가 식별**한다. 마찬가지로 클라이언트가 임의로 사망 결정을 통보하거나 점수 변경을 지시하지 못하게 한다. 0발/사망/라운드 종료/중복 패킷 요청은 거부한다. 정확한 RPC 타입·데이터 필드·변환값은 NGO 버전과 Part 07 확정 후 구현한다.

**검증 원칙과 한계 [확정/구현 해석]:** Host는 비정상 요청을 필터링하되 발사 클라이언트의 명중 순간 화면 상태를 우선 인정한다. Client가 조작한 허위 명중을 완벽히 방어할 수 있는 구조는 아니며, 무거운 Host 재추적·완전 서버 권위 판정으로 바꾸지 않는다. 랙 보정/과거 위치 저장/허용 오차 범위는 Part 07에서 별도 논의한다. Host가 사격을 거부했을 때도 사수는 이미 **총성과 반동**을 보았을 수 있으며, 사망 연출을 취소해야 하는 상황은 발생하지 않아야 한다.

탄약은 Host 최종 권위 값을 가진다. 발사 UI에서 즉시 1 감소시키는 로컬 예측표시를 적용한다면 거부·승인 시 Host 값으로 보정한다 [구현 해석]. 탄약 아이템 보급 및 동시 발사 시 탄약 경합은 Host에서 직렬화한다.

## 03-05. 죽음·동시 사망·라운드 판정과의 결합

- 사망한 플레이어에게는 전신이 쓰러지는 애니메이션과 근거리 3인칭 사망 카메라 1~2초를 표시한 후, 라운드가 끝날 때까지 자유 고스트 카메라를 제공한다 [Part 01 확정]. NPC도 Host 승인을 받은 시점부터 쓰러진다.
- **마지막 생존 판정이 처음 성립했더라도 곧바로 결과 화면을 확정하지 않는다.** Host는 이전에 사용자가 정한 **1초 동시 사망 허용 창**을 유지한다. 그 안에 Host가 승인한 사망 판정은 양쪽 모두 쓰러지는 애니메이션에 반영한다.
- 마지막 두 명이 1초 안에 서로 죽으면 둘 다 쓰러진 화면을 보여주되, **Host가 먼저 승인·처리한 사격으로 상대를 사망시킨 사수**가 라운드 승자이다. 동시 사망 시간 비교 기준, 수신 순서, 이미 죽은 발사자의 인플라이트 요청 수용 범위는 Part 07에서 최종 정의한다.
- Host만 사망 상태, 누적 득점, 라운드 결과를 결정한다. 사망 후 전송된 낡은 요청과 새 라운드에 도착한 이전 라운드 요청은 버린다.
- 라운드 승리 연출은 **시상대가 아닌 원래 맵에서 5초간 승리자를 제3자 시점으로 비추는 것**이며, 3점 선취 매치 종료 시에만 시상대를 보여준다.

# Part 04. NPC 배회 AI · 목적지 가중치 · 풀링 생명주기

> **Part 04 상태:** NPC 행동 정책·수량 산정 원칙·목적지 가중치·풀링/라운드 초기화 규칙 **확정**. 맵 크기별 최종 수치·배치·네트워크 구현 세부값 및 플레이 테스트 튜닝만 추후 진행.  
> **작성일:** 2026-10-12 · **구현:** 아직 미실시. Unity 프로젝트 및 에셋은 수정하지 않음.

## 04-01. 핵심 행동 규칙

1. **[확정]** NPC 수는 라운드 참가 플레이어 수의 `8배`를 초기 시도값으로 사용한다. 맵을 충분히 채우는 것이 목표지만 **이 수치는 확정 밸런스가 아니며** 실제 맵 크기, Host 성능, 클라이언트 FPS 및 네트워크 부하를 측정하여 조정한다. 2~8명이면 시험 수량은 16~64개다.
2. **[확정]** NPC는 플레이어와 동일한 전신 외형, 손에 든 총 모델, 공용 Animator/Blend Tree를 사용한다. **걷기만 가능**하고 달리기·점프·사격하지 않는다. 탄약 아이템도 의도적으로 획득하지 않는다.
3. **[확정]** NPC는 NavMesh 위의 임의 목적지를 선택하여 이동한다. 목적지 도착 후 가끔 짧게 정지하고, 정지 중 주변을 둘러보거나 회전한다. 중간 경로 회전은 NavMeshAgent 이동에 맞춰 자연스럽게 수행한다.
4. **[확정]** NPC를 1발로 죽일 수 있고, **같은 라운드에서 죽은 NPC는 재생성하지 않는다.** NPC를 제거해 위장할 개체 수를 줄이는 것도 허용된 플레이 전략이다. 풀에 반환하는 것은 미래 라운드에서 인스턴스를 **재사용**하기 위함이지, 현재 라운드에서 부활시키기 위함이 아니다.
5. **[확정]** NPC 간 별도의 최소 거리·최대 밀도 제한, 강제 분산, 몰렸을 때 강제 밀어내기는 적용하지 않는다. NPC 바로 옆에 붙어서 이동하는 플레이어의 전략을 허용한다. NavMeshAgent 기본적인 경로/충돌 회피는 사용 가능하나 실제 움직임이 자연스러운지 테스트해야 한다.
6. **[확정]** 목적지 선택의 보정 요소는 **현재 구역별 NPC 밀도**와 **해당 NPC의 최근 방문 구역 기록**이다. 공간 구석 판정용 추가 8방향 탐색, 벽 근접도 Raycast, 수동 `좁은/넓은` 영역 레이블은 **프로토타입에서 사용하지 않는다**.
7. **[확정]** NPC는 **총성, 총격, NPC·플레이어 사망, 시체 발견 등 주변 전투 상황에 반응하지 않는다.** 이 사건으로 목표 지점을 변경하거나 도망·추적·경계·군집·조사·별도 방향 전환을 수행하지 않고, 기존의 무작위 배회·가끔 정지·자율적 둘러보기 규칙을 그대로 유지한다. 전투 관련 감지/반응 AI를 포함하여 **추가 NPC 행동 메커니즘은 도입하지 않는다.** (NPC 자신의 피격 및 Host 사망 승인에 따른 사망 처리는 예외가 아닌 필수 사망 생명주기다.)

## 04-02. NavMesh와 논리적 구역 관리

Unity NavMesh는 **이동 가능한 표면과 경로**만 책임진다. NPC 분포 계산을 위한 구역은 NavMesh 위에 겹쳐지는 **별도의 논리 격자**로 관리한다. 격자 크기는 맵 크기 확정 후 튜닝하며, 실제 플레이에 보이는 지형 구분이나 별도 NavMesh Area 마킹이 필요하지 않다.

- **[구현 해석]** 사전에 각 구역에 유효한 NavMesh 목적지 후보를 준비한다. NPC가 목적지를 바꿀 때 후보를 무작위로 뽑아 접근 가능 경로를 검사하고, 유효하지 않으면 재선정한다. 특정 골목을 수동 제외하는 정책은 두지 않는다.
- **[확정]** NPC의 **현재 위치가 속한 구역별 살아 있는 NPC 수**를 관리한다. 도착지 예약 인원과 개별 NPC 간 최소 거리는 필수 계산 항목이 아니다.
- **[권장]** 구역 밀도는 모든 NPC를 매 프레임 전수 탐색하는 대신 `구역 이동 이벤트`에서 `이전 구역 -1 / 새 구역 +1`로 유지한다. 풀 반환, 사망 시 등록 해제, 라운드 종료·시작 초기화도 같은 API를 통과하도록 한다. 등록 여부 플래그/현재 등록 구역을 두어 **중복 증감**을 방지한다.
- **[권장]** 구역별 후보 지점이 지나치게 적은 작은 통로를 과대표집하지 않도록 후보 지점의 분포를 NavMesh 유효 면적과 연동해 만든다. 이는 맵에 맞춘 구현 최적화이며 지금 사용자 요구에 없는 수동 좁은 구역 구분을 도입하는 뜻이 아니다.

## 04-03. 현재 밀도 + 최근 방문 기록의 목적지 확률

**[확정된 정책]** 목적지는 전체적으로 무작위이며, `현재 밀도가 높은 구역`과 `해당 NPC가 최근 방문한 구역`은 **상대적으로 덜 선호**하도록 한다. 제한이 아니라 확률 보정이므로 이미 사람이 많은 곳, 구석진 장소에도 NPC가 들어갈 수 있다. 어떤 유효 구역에도 가중치를 0으로 설정하지 않는다.

**[구현 제안 — 실제 수치는 추후 튜닝]**

```text
For each NPC when it needs a new destination:
  candidates = random reachable NavMesh points distributed over map zones
  for each candidate:
    densityFactor = f(currentAliveNpcCount[candidate.zone])     // 인원 많을수록 약하게 감소, > 0
    historyFactor = g(npc.recentlyVisitedZoneIds, candidate.zone) // 최근 방문시 감소, > 0
    weight = densityFactor * historyFactor
  destination = weightedRandom(candidates, weight)
  if route invalid: retry with bounded attempts, then safe fallback
```

- **[권장/튜닝]** 방문 이력은 NPC당 최근 **3~5개** 구역 ID를 제한 길이 순환 버퍼로 저장한다. 실제 **새 구역 진입 또는 도착** 중 일관된 한 기준으로 한 번만 기록하고, `Update()`마다 같은 구역을 중복 삽입하지 않는다.
- **[확정]** 이력은 **라운드마다 반드시 비워야 한다.** 이전 라운드 또는 이전 풀 사용 주기의 기록이 새로운 NPC 이동 확률에 영향을 주면 안 된다.
- **[권장]** 밀도 보정, 방문 보정 모두 너무 강하지 않게 하고 이동 결과가 인위적인 정규 분포가 되지 않도록 한다. `W > 0` 불변식과 후보 재시도 상한을 둔다.
- **[확정]** NPC 간 근접 거리나 현재 밀도를 이유로 이동을 강제로 중지/후퇴시키지 않는다. 계산은 **다음 목적지 선택 시점**에만 반영한다.

## 04-04. 이동/정지/둘러보기 상태

```text
Pooled (비활성)
  └─ 라운드 시작 Spawn/초기화 → Walking
Walking
  ├─ 목표 도착 → (확률 선택) Pausing / LookingAround
  ├─ 목표 도착 → (확률 선택) 새 목적지 Walking
  ├─ 경로 오류·정체 → 안전한 목적지 재선정
  └─ Host 사망 확정 → Dying
Pausing / LookingAround
  ├─ 짧은 대기·회전 완료 → Walking
  └─ Host 사망 확정 → Dying
Dying
  └─ 사망 연출 완료/라운드 종료 → Despawn + Pooled
```

- **[확정]** 달리기 상태는 존재하지 않는다. 점프·NPC 사격 상태도 존재하지 않는다.
- **[권장]** 도착 직후 정지 확률, 정지 지속시간(기존 논의의 예시 0.5~2초), 둘러보기 회전량은 모두 임시 테스트값이며 맵 테스트 후 보정한다. `LookingAround`는 공용 Animator로 재생하되 NPC 전용 시각 효과나 별도 모델을 쓰지 않는다.
- **[구현 권장]** 실질적인 NPC 목표 계산·AI 상태 결정은 Host에서만 수행한다. 클라이언트는 NGO를 통해 결과 위치/애니메이션을 받는다. 클라이언트별 독립 난수로 NPC 목적지를 다시 고르지 않는다.
- **[확정]** 총격 또는 주변의 죽음이 발생해도 `Walking / Pausing / LookingAround` 상태 전이를 별도로 일으키지 않는다. NPC가 우연히 같은 시점에 멈추거나 둘러보는 것은 사전에 정한 일반 확률 행동일 뿐, 사건 인식 결과가 아니다.

## 04-05. 오브젝트 풀의 인스턴스 생명주기

**[확정]** NPC 인스턴스는 풀링을 사용해 신규 Instantiate/Destroy 횟수를 최소화한다. 풀링이 기존 Unity/NGO 오브젝트의 상태를 알아서 초기화해 주지는 않으므로, **명시적 생명주기 메서드**와 상태 정리 책임을 설계한다.

```text
PoolAvailable
  → Acquire
  → ResetForRound(roundId)
  → ResetForSpawn(spawnGeneration, spawnPoint)
  → NetworkSpawn / Alive
  → Host death approved: Dying
  → death animation complete (또는 round cleanup)
  → NetworkDespawn / ResetForPool
  → PoolAvailable
```

- **[구현 제안]** Host가 풀의 소유자/활성 NPC 레지스트리를 관리한다. `NPCManager`는 NPC 오브젝트의 현재 상태가 `PoolAvailable / Alive / Dying` 중 하나인지를 일관되게 관리하고, `NPCPool`은 렌더러/Collider/NetworkObject 단위 재사용을 담당한다.
- **[확정]** **동일 라운드 사망 → 같은 라운드 재활성화 금지.** 죽은 NPC를 풀에 넣어도 `currentRoundId`의 NPC 수량 부족을 채우는 용도로 꺼내지 않는다. 정상 다음 라운드 또는 명시된 새로운 라운드 시작에서만 다시 사용한다.
- **[권장]** Host NGO 풀 구현 시 `NetworkObject.Spawn/Despawn` 순서와 클라이언트의 풀 인스턴스 재사용을 함께 맞춘다. `INetworkPrefabInstanceHandler` 등 NGO 버전별 API 적용은 **프로젝트 패키지 버전 확인 후 Part 07에서 확정**한다. 일반 `SetActive`만으로 Host/Client 네트워크 Spawn 동기화가 보장된다고 가정하지 않는다.
- **[권장]** 풀 크기는 첫 라운드 시작 시 필요한 개수까지 예열하고, 이후 수요 증가 시 풀 확장을 허용한다. 인원·라운드 변화로 남는 풀 오브젝트는 휴면 상태로 보관하되, 실제 메모리 예산은 성능 테스트 후 정한다.

## 04-06. 라운드 초기화·활성화·반환 명세

정상 라운드 전환뿐 아니라 **다시하기 만장일치로 라운드 무효화**, 도중 강제 종료, Host 이탈, 씬 전환에도 동일한 Cleanup 경로를 사용해야 한다.

| 시점 | 반드시 초기화/정리할 사항 | 주의할 실패 사례 |
|---|---|---|
| `BeginRound` 진입 전 | 이전 `roundId`의 모든 AI 작업 정지, 활성 NPC 회수, 구역별 밀도 0으로 초기화, 중복 등록 검증 | 이전 라운드 NPC가 새 라운드 첫 프레임에 목적지 변경 |
| `ResetForRound` | `roundId` 갱신, NPC별 `recentZoneHistory.Clear()`, 마지막/현재 구역 무효화, 목적지 기록·랜덤 AI 상태 초기화 | 재활용 NPC가 전에 갔던 구역을 피함 |
| `ResetForSpawn` | `generationId` 증가, 사망 플래그/체력 복구, NavMeshAgent 이동 정지·`ResetPath`·유효 위치 `Warp`, 새 목적지 선택 가능 상태 복구 | 이전 목적지로 순간 이동, 잘못된 경로 유지 |
| `ResetForSpawn` 시각 | Animator 파라미터·Trigger 정리, 기본 Idle 지정, 사망 연출 흔적/코루틴/타이머 제거, CapsuleCollider 활성화, 렌더러/총 모델 정상화 | 시체 자세로 새 라운드 시작, 피격 불가 |
| 스폰 직후 | 구역에 **한 번만** 등록, Alive 상태로 공개, Host AI 이동 시작; 네트워크 스폰/위치 갱신 순서 보장 | 밀도 두 번 증가, 클라이언트가 이전 위치를 봄 |
| 일반 이동 중 | 구역이 바뀌면 이전 -1, 새 +1; 실제 새 방문을 이력에 기록, 목표 도착/실패 시만 가중치 갱신 | 밀도가 지속적으로 누적, Update마다 이력 중복 |
| `OnDeathApproved` | Alive→Dying **한 번만** 전환, 목적지/Agent 정지, 밀도 등록 제거, 피격 재요청 거부, 사망 모션 브로드캐스트 | 중복 사망·중복 밀도 -1, 이동 중 시체 미끄러짐 |
| `ReturnToPool` | 사망 애니메이션 표시 완료 보장, 네트워크 despawn 처리, 남은 이동·코루틴·콜백 종료, 경로·상태·충돌 정리, 풀 반환 1회 | 중간에 시체 소실/풀에 동일 인스턴스 중복 반환 |
| 강제 종료/Redo | 완료되지 않은 사망/정지 타이머도 취소, 모든 개체 일괄 회수, 구역 밀도 리셋, 라운드별 예약/방문 기록 폐기 | Redo 이후 구 라운드 콜백이 새 NPC를 사망 처리 |

**[구현 권장]** 비동기 코루틴, Delay, 네트워크 이벤트마다 `roundId + spawnGeneration`을 검증한다. 이전 라운드·이전 풀 사용 주기의 콜백은 새 인스턴스에 적용하지 않는다. 활성 레지스트리/구역 등록에는 `isRegistered` 같은 보호 장치를 둔다. 부활 시 `OnEnable()` 하나에 의존하지 않고, `ResetForRound`, `ResetForSpawn`, `ResetForPool`을 명확히 분리한다.

**[구현 해석]** 사망 상태 NPC는 **살아 있는 NPC 구역 밀도에 포함하지 않는다.** 사망 애니메이션을 유지하다 반환하므로 렌더링 종료 시점과 밀도 집계 해제 시점은 다를 수 있다. 모든 클라이언트의 사망 연출 시작은 Part 03의 Host 최종 승인 이후다.

## 04-07. NPC 수량/라운드 중 입퇴장과 풀 관리

- **[구현 해석]** 초기 NPC 수량 기준은 **라운드 시작 시 실제 게임에 참여하는 플레이어 수**다. 로비 참가자와 라운드 중간에 들어와 다음 라운드까지 관전하는 참가자를 구별한다.
- **[권장: 추후 Part 06·07 확정]** 라운드 도중 플레이어가 퇴장하더라도 시작 시 소환한 NPC를 수량 조절 목적으로 사라지게 하지 않고, 늦게 들어온 플레이어 때문에 새 NPC를 소환하지 않는다. 라운드 시작 시점에 결정된 NPC 수량은 사망에 의해서만 감소한다.
- **[확정]** 라운드에서 NPC 사망 후 리스폰 없음. **[권장]** 다음 라운드는 새 `roundId`와 새 `spawnGeneration`으로 풀의 개체를 재사용한다.

## 04-08. 성능 최적화 및 QA

- **[권장]** 목적지 후보 리스트·구역 매핑은 맵 준비 단계에 구축하고 라운드마다 구조물을 다시 계산하지 않는다. 각 NPC는 목적지 도착/실패 시에만 랜덤 후보 및 가중치 처리한다.
- **[권장]** NPC AI 계산은 Host에서만 처리하고, NPC Transform·Animator 동기화 비용은 Part 07에서 NGO 방식에 따라 검증한다. `16/32/48/64 NPC × 2~8 players` 환경에서 서버 프레임·클라이언트 FPS·네트워크 데이터량을 측정한다.

| QA ID | 상황 | 기대 결과 |
|---|---|---|
| C04-001 | 2~8명으로 라운드 시작 | 시작 인원×8 NPC 임시 목표. 실제 성능 따라 수치 조정 가능 |
| C04-002 | 임의 NPC가 밀집 구역 선택 | 가중치만 낮을 뿐 선택 가능. 강제 분산·거리 제한 없음 |
| C04-003 | NPC가 같은 구역에서 여러 프레임 머묾 | 방문 이력 중복 기록·밀도 중복 증가 없음 |
| C04-004 | NPC가 구역 A→B 이동 | A -1 / B +1이 정확히 한 번 반영됨 |
| C04-005 | NPC가 정지·둘러보기 | 달리기·사격·점프 없이 공용 Animator 동작 |
| C04-006 | NPC 사망 | Host 승인 후 사망 애니메이션, 이동 중단, 중복 사망 방지 |
| C04-007 | 라운드 중 NPC 사망 다수 | NPC 수가 감소하며 **같은 라운드에 다시 증가하지 않음** |
| C04-008 | 라운드 종료→다음 라운드 | 모든 최근 방문 이력 비어 있고 구역 밀도 다시 정확히 구성됨 |
| C04-009 | Redo로 라운드 무효화 | 기존 루틴 취소, AI/Animator/경로 초기화, 새 라운드 방문 이력 없음 |
| C04-010 | 풀 개체 사망 애니메이션 후 반환→재사용 | 사망 잔상·콜라이더 비활성·이전 목표·중복 등록 없음 |
| C04-011 | 라운드 A의 지연 콜백이 라운드 B에 도달 | ID/generation 검증 실패로 무시됨 |
| C04-012 | 최대 NPC 수량·다수 Client 연결 | 성능 계측 결과로 배수·보간·전송율 등 튜닝 근거 확보 |
| C04-013 | NPC 근처에서 플레이어가 사격하거나 다른 NPC가 죽음 | 주변 생존 NPC가 소리/시체 인식에 따른 회피·추적·조사·경계·강제 회전을 하지 않고 기존 배회/정지/둘러보기 상태를 이어감 |
| C04-014 | NPC가 사망 연출 중이거나 시체가 보이는 지점 근처에 NPC가 존재 | 주변 NPC는 별도 반응 없이 일반 NavMesh 배회만 유지함; 자신의 사망 승인 이벤트는 정상 처리 |

## 04-09. 아직 확정되지 않은 사항

1. **[추후 튜닝]** 실제 맵의 구역 셀 크기, NavMesh 후보 간격, 이동 속도(Part 02 공용 걷기 속도 참조), 가중치 구체 공식/강도, 방문 기록 길이, 정지 확률·지속시간, 둘러보기 회전 강도.
2. **[추후 Part 05]** NPC 최초 등장 위치·스폰 가능 공간·NPC/플레이어 초기 배치 분포와 맵 지형 충돌 방식.
3. **[추후 Part 07]** NGO 풀의 Host/Client 인스턴스 재사용 방식, NetworkTransform/Animator 전파 정책, 네트워크 동기화 비용, 연결·재접속 예외와 풀 초기화 순서.
4. **[확정 — 추가 논의 불필요]** NPC의 총성·사망·시체 반응은 **없음**. 현재 배회·정지·둘러보기·피격/사망 외 NPC 행동 메커니즘을 추가하지 않는다.
5. **[미구현]** Unity의 NavMesh, 프리팹, Animator, Script, Pool 실제 생성·임포트는 아직 수행하지 않았다.
